# COIN-IDEAL Deployment Architecture

## Pipeline (EXISTING — entirely manual, no CI)

```
LOCAL DEV
  npm run dev (Vite dev server, port 5173 default)
      ↓
  git commit + git push (main branch — no feature-branch/PR workflow
    observed in this project's own history; commits go straight to main)
      ↓
VERCEL (automatic Git-integration deploy on push — no GitHub Actions,
  no staging environment, no approval gate)
      ↓
PRODUCTION (https://coin-ideal-app.vercel.app)
```

There is **no STAGING or QA environment distinct from production** in this
architecture — `docs/phase-5/PHASE_5D_VERCEL_STAGING_REPORT.md`'s title
notwithstanding, all live-account testing throughout this project's history
has been performed directly against the production Vercel URL and the one
linked Supabase project. **RECOMMENDED**: introduce a Vercel preview
deployment + a second Supabase branch/project for true pre-production
testing if the business's risk tolerance requires it; not present today.

## Vercel (EXISTING)

Configured via `vercel.json` (repo root):
```json
{
  "buildCommand": "npm run build",
  "outputDirectory": "dist",
  "framework": "vite",
  "rewrites": [{ "source": "/((?!assets/).*)", "destination": "/index.html" }]
}
```
The rewrite rule is what makes client-side routing (React Router) work on
a static host — every path except `/assets/*` serves `index.html`, letting
the SPA's router take over. **Required environment variables** (Vercel
project settings, not in the repo): `VITE_SUPABASE_URL`,
`VITE_SUPABASE_ANON_KEY` (both public/anon-safe — see
`docs/architecture/SECURITY_ARCHITECTURE.md` for why these two, and only
these two, are safe to expose to the browser). No `.vercel/` directory is
committed (project is linked via the Vercel dashboard's Git integration,
not the Vercel CLI).

## Supabase Cloud (EXISTING)

Project ref `qqibjglnvcezqbogkvlg`, name `coin-ideal-app` — the **only**
legitimate project for this codebase (see
`docs/architecture/ARCHITECTURE_RULES.md` rule 15 and `CLAUDE.md`'s
documented incident about a differently-linked local CLI once seeing an
unrelated "NKDELIVERI" project). Linked locally via `supabase link
--project-ref qqibjglnvcezqbogkvlg`, recorded in
`supabase/.temp/project-ref` (gitignored, regenerated by `supabase link`).

**Migrations**: `npx supabase db push --linked` applies any migration in
`supabase/migrations/` not yet recorded as applied on the linked project.
**Always preceded by `--dry-run`** to review the exact file list before a
real push, and always followed by an explicit human confirmation in this
project's established workflow (see `CLAUDE.md` rule 3, and
`docs/architecture/TESTING_ARCHITECTURE.md`).

**Edge Functions**: `npx supabase functions deploy <name>` per function
(`ai-assistant`, `register`). Secrets are set once via `npx supabase
secrets set KEY=value` (never through this codebase's own tooling, and
never visible after — `supabase secrets list` only returns masked hashes).
Current secrets in use (names only, per `docs/architecture/SECURITY_ARCHITECTURE.md`):
`GEMINI_API_KEY`, `ALLOWED_ORIGINS`, plus the platform-injected
`SUPABASE_URL`/`SUPABASE_ANON_KEY`/`SUPABASE_SERVICE_ROLE_KEY`/`SUPABASE_DB_URL`
(automatically available to every Edge Function, never manually set).

**`supabase/config.toml`** — **important caveat, EXISTING and previously
misleading**: this file configures the **local** Supabase stack
(`supabase start`) only. Its `[auth] site_url`/`additional_redirect_urls`
values (`http://127.0.0.1:3000`) are scaffold defaults that were **never
aligned with the real remote project's Auth settings** — confirmed during
this project's own Phase 6 work, where `supabase config push` was
deliberately **not** run for exactly this reason (it would have overwritten
the live project's real `site_url`/redirect allow-list with these
placeholder values, breaking OAuth/email-confirmation redirects in
production). **Do not run `supabase config push` against this project
without first editing these values to the real production URL** — see
`docs/architecture/DECISIONS.md`.

## Safe local operations vs. production operations

| Operation | Safe locally, always | Requires explicit confirmation before running against the linked project |
|---|---|---|
| `npm run dev` / `npm run build` | ✅ | n/a |
| `npx tsc -b`, `npx oxlint` | ✅ | n/a |
| `supabase db push --dry-run --linked` | ✅ (read-only preview) | n/a |
| `supabase db push --linked` (real) | ❌ | ✅ — dry-run reviewed first, per `CLAUDE.md` rule 3 |
| `supabase db reset` (local Docker stack) | ✅ (only touches local containers) | n/a |
| `supabase functions deploy <name>` | ❌ (always hits the linked project) | ✅ |
| `supabase secrets set` | ❌ | ✅ — and the value must come from the user's own terminal, never chat |
| `auth.admin.deleteUser()` / any Storage delete via service-role | ❌ | ✅ — requires the service-role key, which this session never handles directly; see `docs/phase-6/QA_TEST_ACCOUNTS_CLEANUP_REPORT.md` for the established pattern (verify exact targets first, execute only on explicit confirmation) |
| `git push origin main` | ❌ (visible to others, deploys automatically via Vercel's Git integration) | ✅ |
| `supabase config push` | ❌ | **Do not run without first fixing `site_url`/redirect URLs** — see above |

## Rollback (RECOMMENDED — not formally documented as an existing runbook)

- **Frontend**: Vercel retains every previous deployment; rolling back is a
  dashboard action (promote a previous deployment) — not scripted in this
  repo.
- **Database**: migrations are additive/forward-only by this project's own
  rule (never edit a deployed migration) — a "rollback" is a new,
  forward-fixing migration that reverses the effect, not a `down`
  migration. No `down`/reverse migrations exist in `supabase/migrations/`
  today; **RECOMMENDED** to write one alongside any migration whose effect
  might need fast reversal (e.g. a new RLS policy that turns out too
  permissive).
- **Database backup**: not documented in this repo; Supabase Cloud provides
  automatic backups per its own plan tier — verify current retention in
  the Supabase dashboard, not tracked here.

## Environment variables (EXISTING, complete list)

| Variable | Where | Safe to expose to browser? |
|---|---|---|
| `VITE_SUPABASE_URL` | Vercel env, local `.env` | ✅ yes (public project URL) |
| `VITE_SUPABASE_ANON_KEY` | Vercel env, local `.env` | ✅ yes (anon key, RLS-scoped by design) |
| `SUPABASE_SERVICE_ROLE_KEY` | Edge Function secret only, platform-injected | ❌ **never** |
| `GEMINI_API_KEY` | Edge Function secret only | ❌ never |
| `ALLOWED_ORIGINS` | Edge Function secret only | n/a (server-side CORS config) |

`.env.local` (gitignored) is used during local development specifically to
point at a **local** Supabase stack (`http://127.0.0.1:54321`) when Docker
is available; when it isn't, this project's own sessions have repeatedly
worked around it by temporarily renaming `.env.local` aside so `.env`
(pointing at the real linked Cloud project) takes effect for local dev
testing — a documented, reversible, deliberate workaround, not a
permanent config change.
